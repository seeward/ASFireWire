# M-Audio FireWire 1814 — Device Reference

Everything ASFW knows about this device, gathered from the wire, the device's own
diagnostic shell, its firmware image, and the in-tree reference stacks.

Claims are marked **[measured]** (observed on hardware), **[derived]** (computed
from a reference implementation and cross-checked), or **[unverified]**.

## 2. Bring-up: the two things that were actually broken

Both failures were self-inflicted by ASFW, and **neither was on the wire**. This
section exists because a long investigation aimed at packet contents while the
packets were already correct.

### 2.1 The driver muted the device (capture silent)

ASFW sent M-Audio clock source operand `0` — `InternalDigitalMute`. On this
firmware that operand *mutes the digital path*; the selector FB 4 that follows is
**the release**, not decoration. ASFW sent both, but both *before the plugs were
connected*, so the release never landed on anything.

Symptom: the device transmitted **only 8-byte NO-DATA packets, indefinitely**.
The vendor's own capture shows the clock frame alone driving output from
`Largest 552` down to `8`, and only the selector restoring it (`-> 360`).

Fix: adopt Linux's policy — source `Internal` (operand `3`), no selector, which
needs no release (`bebob_maudio.c:276`). Landed in `9ffce214`.

**[measured]** symptom and **[derived]** mechanism; a controlled A/B (revert to
operand 0, confirm the drop to 8-byte packets) has **not** been run.

### 2.2 The driver wiped the mixer (playback silent)

`SendParameterBlock` asserted all 40 quadlets of the parameter window, and the
device's four **signal-routing registers live inside that window** at
`+0x90..0x9c`. Every bring-up therefore cleared the mixer.

`fw mix show` reported *"There are no connections!"* and every physical output
metered exactly `0x00000000` while a perfectly healthy stream arrived.

This came from porting FFADO's `Mixer::initialize` faithfully — but FFADO ships a
mixer GUI to refill the matrix, and ASFW does not, so a cleared matrix is
permanent silence.

Fix: assert routing defaults instead of zeros. Landed in `80fc841b`,
**[measured]** on a fresh install at a new bus generation.

## 3. Stream geometry

### 3.1 Formation table

Channel counts are **not discoverable** — `PLUG_INFO` is unsafe on this firmware
— so they are asserted from Linux `bebob_maudio.c:227-254`
(`ASFWDriver/Audio/Protocols/BeBoB/MAudioSpecialFormation.hpp`).

Indexed `[digital format][rate band]`. Bands pair adjacent rates:
`0 = 44.1/48`, `1 = 88.2/96`, `2 = 176.4/192`.

| direction | S/PDIF | ADAT |
|---|---|---|
| capture (device→host) | 10, 10, 2 | 16, 12, 2 |
| playback (host→device) | 6, 6, 4 | 12, 8, 4 |

Plus **one MIDI/conformant-data block per direction at every rate**. DBS is
PCM + MIDI, not PCM alone.

### 3.2 Verified at 48 kHz / S/PDIF

| | table | wire | agree |
|---|---|---|---|
| capture | 10 + 1 = **DBS 11** | `020b00c8` → `0x0b` | ✓ |
| playback | 6 + 1 = **DBS 7** | `00070020` → `0x07` | ✓ |

**[measured]**, and independently corroborated by `fw show` reporting
`Input Source = SPDIF` / `Output Source = SPDIF`.

### 3.3 The digital-format hazard

`MAudioSpecialProtocol.hpp:113-114` **hardcodes** `captureFormat_ = SPDIF` and
`playbackFormat_ = SPDIF`, and never asks the device. Today that matches — by
coincidence, not negotiation.

A unit that boots in ADAT would report ADAT while ASFW asserts the S/PDIF
geometry, and the stream shape goes **silently wrong** (capture 16 vs 10,
playback 12 vs 6). This is now *detectable* via `fw show`, and nothing yet acts
on it. Open.

## 4. Wire format (48 kHz, S/PDIF, blocking)

All **[measured]** from a FireBug capture with audio running.

### Device → host, iso channel 1 (`SwSend`), 360 bytes

```
020b00c8  9002f2b6  400000e3 40000057 …
```
| field | value |
|---|---|
| SID | `2` — the device's node ID |
| DBS | `0x0b` = 11 |
| DBC | `0xC8` |
| FMT | `0x10` (AM824) |
| FDF | `0x02` (48 kHz) |
| SYT | `0xF2B6` |
| payload | `0x40` AM824 PCM labels |

`360 = 8 + 11 × 4 × 8` (CIP header + DBS slots × 4 bytes × 8 data blocks).

Interleaved with 8-byte NO-DATA at roughly 1-in-4: `02020 0d0 / 9002ffff`
(DBS 2, FDF `0xFF`, SYT `0xFFFF`). Normal blocking-mode cadence.

### Host → device, iso channel 0 (`SwReturn`), 232 bytes

```
00070020  90020200  4005c1be 40011519 …
```
SID `0` (our node ID), DBS `0x07`, FDF `0x02`, SYT `0x0200`, `0x40` PCM labels
with `0x80000000` in every 7th slot (the MIDI/conformant block).
`232 = 8 + 7 × 4 × 8`.

Cadence packets: `00070018 / 90ffffff`, `0xCF` fill, `0x80000000` every 7th
quadlet — full-size, not header-only.

Measured ratio **0.7498** data-to-total, ≈6047 data + ≈2039 empty per second.

## 5. Clock model

From `/cfg/dev/isodrv/ClockDividers` — all **[measured]**.

### 5.1 `divSyncDiv` is per rate *band*, not per rate

The IEEE 1394 cycle timer runs at **24.576 MHz** (3072 ticks × 8000 cycles/s).

| band | rates | divSyncDiv | 24.576 MHz ÷ rate | exact |
|---|---|---|---|---|
| 0 | 44100 / **48000** | 512 | 557.279 / **512.000** | 48 k only |
| 1 | 88200 / **96000** | 256 | 278.639 / **256.000** | 96 k only |
| 2 | 176400 / **192000** | 128 | 139.320 / **128.000** | 192 k only |

Same banding the formation table uses. `sys tgen` independently reports
`Synchronization Source: CTR`, confirming the device derives its sample clock
from the bus cycle timer.

### 5.2 `divVco / divRefDiv` is the ×Fs multiplier, and identifies the source

Measured at 48000 across all three subtrees:

| source | divVco | divRefDiv | ratio | note |
|---|---|---|---|---|
| `syt` | 16384 | 4 | **4096 × Fs** | |
| `csp` | 12288 | 4 | **3072 × Fs** | 3072 = ticks per isoch cycle |
| `dars` | 4096 | 8 | **512 × Fs** | |

`divFS256_1` = `divFS256_2` = `1` everywhere (the standard 256×Fs master clock —
12.288 MHz at 48 k).

`dars` exists for only four rates (44100–96000); `syt` and `csp` cover all six.

### 5.3 The 44.1 family

`divVco` and `divRefDiv` are **identical at all six rates**, so the ~8%
correction the 44.1 family needs is *not* in this configuration. It must be the
DCO trim the PLL calibration loop settles at runtime — the source of the endless
`DM1001 digital pll calibration... done.` chatter when the device is unanchored.
Mechanism **[unverified]**.

## 6. Mixer and routing

### 6.1 The parameter window — `0xFFC7 : 0x00700000`, 40 quadlets (`0x00..0xA0`)

Layout **[derived]** from the ALSA userspace BeBoB crate,
`protocols/bebob/src/maudio/special.rs`:

| offset | content |
|---|---|
| `0x00–0x08` | stream input gains |
| `0x08–0x10` | analog output volumes |
| `0x10–0x20` | analog input gains |
| `0x20–0x24` | S/PDIF input gains |
| `0x24–0x34` | ADAT input gains |
| `0x34–0x38` | aux output volume |
| `0x38–0x40` | **headphone volumes** |
| `0x40–0x50` | analog input balance |
| `0x50–0x54` | S/PDIF input balance |
| `0x54–0x64` | ADAT input balance |
| `0x64–0x6c` | aux stream input gains |
| `0x6c–0x7c` | aux analog input gains |
| `0x7c–0x80` | aux S/PDIF input gains |
| `0x80–0x90` | aux ADAT input gains |
| **`0x90–0x94`** | **routing: phys → mixer** |
| **`0x94–0x98`** | **routing: stream → mixer** |
| **`0x98–0x9c`** | **routing: headphone pair source** |
| **`0x9c–0xa0`** | **routing: analog output pair source** |

Gains/volumes are big-endian `i16` with `0` = maximum. Balance registers are
hard-panned as `0x7FFE8000`.

Meter block lives separately at `0xFFC7 : 0x00600000` (84 bytes).

> The parameter window appears to be **write-only** — reads at `+0x700090` time
> out while the meter window at `+0x600000` reads fine. **[measured]**

### 6.2 Routing register encoding and defaults

| offset | encoding | default | meaning |
|---|---|---|---|
| `0x90` | bitmask | `0x00000000` | no physical input into the mixer |
| `0x94` | `1 << (pair*2 + mixer)` | `0x00000009` | stream pair 0→mixer 0, pair 1→mixer 1 |
| `0x98` | `flag << (pair*16)`; Mix0=`0x01`, Mix1=`0x02`, Aux0=`0x04` | `0x00020001` | both headphone pairs follow their mixer pairs |
| `0x9c` | `flag << pair`; Mixer=`0x00`, Aux0=`0x01` | `0x00000000` | analog outs take mixer output |

ASFW asserts these in `MAudioSpecialProtocol::SendParameterBlock`; test coverage
in `MAudioSpecialInitTests.AssertsMixerRoutingSoStreamsReachTheOutputs`.

### 6.3 Mixer as the device names it (`fw mix`)

```
inputs : linein1..linein4, spdif, i14s1..i14s7, adatin1..adatin4
outputs: lineout1, lineout2, spdif, adatout1..adatout4
```

**`i14sN` is a stereo pair, not a channel**: `i14s1 → I14S(ch1,ch2)`,
`i14s2 → I14S(ch3,ch4)`. Seven of them, matching playback DBS 7.

`fw mix connect <input> <output>` / `disconnect` / `reset` / `show`.

### 6.4 Volume (`fw vol`)

Blocks: `lineout1, lineout2, spdifout, adatout, auxout, headphone1, headphone2,
linein, auxlinein, spdifin, auxspdifin, adatin, auxadatin, i14s, auxi14s`.
Range **−128…0 dB**. `fw vol set <block> <level> [channel]`, channel 0 = master.

`fw vol peak` is the meter readout; `fw vol show` the levels; `fw vol dac` the
DAC registers.

> All of this is **volatile**. A dext install re-asserts the parameter window,
> which resets headphone volume to 0 dB and re-applies the routing defaults.

### 6.5 Iso channel assignment (`fw show`)

```
LineIn 62   SpdifAdatIn 61   SpdifAdatOut 58   MixerOut 60
SwReturn 0  SwSend 1         MidiIn/MidiOut/DataOut/AC3 = -1
```
`SwReturn` = host→device, `SwSend` = device→host. Plug counts from
`/cfg/1394`: **3 iPCR, 2 oPCR**.

## 7. The `/cfg` configuration tree

Readable through the shell with plain `ls` — `d.` is a directory, **`.a` is an
attribute whose value `ls` prints inline**. `get <name>` reads a single leaf.
`cd ..` works; `cd /` is rejected (the tree is rooted at `/cfg`); `ls -r` does
**not** recurse; sibling paths like `cd ../48000` fail — use absolute paths.

```
/cfg
├── Shell  FW106  SystemConfig  System  TCP_IP
├── 1394
│   ├── ConfigurationRom, MDB
│   ├── .a NumberOfIPCR = 3
│   └── .a NumberOfOPCR = 2
└── dev
    ├── isodrv
    │   ├── StateMachine
    │   │   ├── .a maxQueueEmpty = -1
    │   │   └── .a stateMachineHeartBeat = 0x2000
    │   └── ClockDividers/{syt,csp,dars}/<rate>/
    │       └── .a divSyncDiv, divVco, divRefDiv, divFS256_1, divFS256_2
    ├── AVC
    │   ├── SubUnit:8          — AV/C descriptor-list metadata, no FCP needed
    │   └── StreamFormatInfo/AnM/AM824/{60958-3, 61937-3}
    ├── SwitchMatrix/{MtxSel0, MtxSel1}
    └── spi, i2c, uart1, uart2, uart1394, uartCombo, tty, ttyBuffer
```

**Significant:** plug counts and AV/C descriptor metadata are readable here with
no FCP traffic at all — and `PLUG_INFO` is precisely the command that is unsafe
on this firmware.

**Ruled out:**
- `StreamFormatInfo` is the **AM824 label taxonomy** (which IEC formats may ride
  in the stream), *not* the channel formation table.
- `SwitchMatrix` is **chip pin-muxing**, not audio routing —
  `SWMATRIX[5:8]=GPIO_FPGA, [3:4]=UART1, [2]=Sync, [0:1]=UART2`, plus test-mode
  and tristate control in `MtxSel0`.

## 8. Diagnostics

### 8.1 `sys stat` — isochronous counters

A **three-column table, one column per iso channel, no colons.** (Note:
`BeBoBStreamTelemetryParser` currently parses an invented `rxPackets: 12450`
shape and its unit tests pass against that fixture — it does not match reality.)

Sections: global (`rxIsr`, `txIsr`), Output Stream (`txWrite`, `txReady`,
`txDelayed`, `txDma`, `txQFillLevel`, `SytOffset`, `FFLimit`), Input Stream
(`rxPackets`, `onlyHeaders`, `rxEmptyPkt`, `rxNoMem`, `CtrDiffErr`,
`SytDiffErr`, `SumDiffErr`, `BCOHdrErr`, `rxQFillLevel`, `PoolFillLevel`).
Rows are prefixed `W` (warning), `E` (error) or `S` (status).

### 8.2 `sys avstat all` — silicon latches

Blocks: TGEN (`FE700000`), AV1 (`FE900000`), AV2 (`FEA00000`),
FRAMER/DEFRAMER (`FED00000`), MDB (`FEE00000`), LLC (`FEF00000`).

Every latch is printed **unconditionally** as `SetTgInLock : 00000001`, so
*presence of the label means nothing* — only the value does.

**These are sticky.** To tell a live fault from a power-on artifact:

```
sys avstat clr all      # prints, then clears
<soak while streaming>
sys avstat all          # whatever re-set is live
```

Usage: `sys avstat [clr] [tgen] [av1] [av2] [av] [frm] [mdb] [llc] [all] [full] [short]`.
`sys av` and `sys tgen` are **different handlers** from `sys avstat`.

### 8.3 Other

- `fw show` — audio state, sync source, rate, iso channels *(prefer over
  `fw sync show`, which reports only the sync source)*
- `sys tgen` — PLL lock, sync source, VCO/divider state
- `sys info`, `sys ver` — board and firmware identity
- `os th` — RTOS thread table; `*`/`**` mark **absolute stack headroom**, not
  percentage (`scTxDMAEnd` at 183/256 = 73 bytes free earns `**`, while
  `M-Audio FW106` at 1787/2048 = 261 bytes free is unmarked)

## 9. Live measurements — 2026-08-17, 48 kHz, audio playing

Deltas over 12.3 s with ~220 k packets:

| counter | ch 0 (host→device) |
|---|---|
| `rxPackets` | 6047/s |
| `rxEmptyPkt` | 2039/s (ratio **0.7498**) |
| `onlyHeaders` | **0** |
| `BCOHdrErr`, `CtrDiffErr` | **0** |
| `rxNoMem`, `rxQFull` | 0 |
| `SytDiffErr` | 0/s steady-state (see below) |

Silicon after a clear-and-soak: `SetTgInLock = 1`, `SetTgSytMiss = 0`,
`DBCMismatch` / `FMTMismatch` / `HeaderMismatch` / `CIPMismatch` all `0`.
Still set: `SIDMismatch`, `SetPhaseErrUpdate`. Did **not** re-arm (power-on
artifacts): `AV1 SetTSErr`, `SyncWarn`, MDB `IsoTXalarm`.

`fw show`: 48 kHz, `Sync Source = INTDIG`, **`Audio State = Running`**.

RTOS: `Mixer` 667,931 runs, `scTxDMAEnd` 657,552 (they track within 1.6% — the
mixer runs once per TX DMA completion), `scRxDMAEnd` **1** *(unexplained)*.
`Mixer` is the only thread with a preemption threshold below its priority
(`9/5/1`), so once running only the priority-4 DMA handlers may preempt it.

**Re-measured over a clean 35 s window with audio playing** (207,448 packets):
`SytDiffErr`, `onlyHeaders`, `BCOHdrErr`, `CtrDiffErr` and `rxNoMem` were all
**0**, and the cadence was exactly **0.750000** (5990.95 data / 1997.06 empty per
second). The ~1.4/s `SytDiffErr` seen earlier was transient settling, not a
steady-state fault.

`scRxDMAEnd` remained at **1** after 26.8 M `scTxDMAEnd` completions, so it is a
one-shot handler rather than a per-packet one — the RX ring is armed circularly
and never signals completion. Not a defect.

Dozens of shell commands, a full `/cfg` walk, `os th` and a latch clear all ran
concurrently with live playback without disturbing the stream: **the Virtual UART
is non-invasive against a running stream.** [measured]

### On `SIDMismatch`

Both directions carry the **correct** SID on the wire (host = 0 = `localNodeId`,
device = 2). Firmware `setFramerSID()` (`sub_201014A0`) programs the framer's SID
register from the device's *own* `bmGetLocalNodeID`, so a remote talker's SID can
never match it. Most likely informational — **do not re-chase**. **[derived]**

Separately: `AudioStreamConfig::sid` defaults to `0` and is **never assigned from
the OHCI NodeID register**, despite `CIPHeaderBuilder.hpp:40` documenting exactly
that. Harmless only while we are node 0. Real latent bug, still open.

## 10. Do not run

| command | why |
|---|---|
| `cfg setdefault` | factory reset of the whole config tree |
| `emu burn`, `emu bitFileToFlash` | writes the FPGA bitfile to flash |
| `SetDTCP` | overwrites the DTCP key |
| `sys reset` | resets the device |
| `wr <addr> <value>` | arbitrary ARM memory write — identify the address in IDA first |
| `bm busreset` | recoverable, but drops the stream and re-enumerates |
| `w 1 stop` / `step` | halts the Warp DSP — kills audio mid-stream |

Mailbox opcodes `0x04`/`0x05`/`0x06` (flash download) and `0x0a`/`0x0b`/`0x10`
(EEPROM GUID/MAC/HWID) are **forbidden** and gated in ASFW.

## 11. Open questions

1. **Capture end-to-end.** Playback is proven CoreAudio→DAC. Capture is proven
   only as far as "packets leave the device" — nothing shows CoreAudio receiving
   audio.
2. **The clock-policy A/B.** Reverting to operand `0` should drop the device to
   8-byte packets. Would convert §2.1 from strong inference to fact.
3. **The 44.1-family clock mechanism** (§5.3).
4. **Rates other than 48 kHz.** 44.1 shares band 0. 88.2/96 is band 1. **176.4/192
   is band 2 and a completely different shape** (capture 2, playback 4), never
   exercised.
5. **MIDI.** The formation reserves one conformant-data block per direction —
   the `+1` in DBS 11 and 7 — but `fw show` reports MidiIn/MidiOut unassigned.
6. **ADAT digital format** (§3.3) — half the formation table is untested and
   nothing reads the device's actual setting.
7. **Bus reset / hot-unplug recovery** — unverified.
